# 根页语义测试：真实数据库录入不能等待界面假时钟

产品基线 `3ee66d50f2e91f98927bb54d61de4a7832befafc`，2026-11-26。本改动仅调整验收夹具，不涉及产品接口、编译输入、数据库表或用户数据。Windows 和 Android 成品仍对应上述提交。

## 场景、红门和原因

Windows 根页面启用辅助功能，鼠标逐页进入发现、搜索、收藏、最近播放、设置和各浮层。到最近播放页时，门用真实数据库录入一首歌，再检查该页控件及语义。冻结提交无筛选全量运行到这条用例时，已通过 1,358 项，原生报告耗时 10 分钟后超时；下一变体也报告失败。首轮已停止，未完成的文件不能计入通过。

在同一提交的独立副本，仅对这次真实录入加 8 秒诊断计时，原场景 `00:25 +0 -1`：`recordListen` 在主区 3 超时。最近播放的串行队列使用创建时钟；原夹具在界面的假时钟里首次创建服务，却在 Flutter 暂停假时钟的 `runAsync` 中等待队列的回调。SQLite 本身正常，正式依赖文件已与发布版本的 SHA-256 比对。

## 处理、验收和回滚

在 `test/ik_semantics_tree_test.dart` 的 `mountRoot` 中，构造 `ProviderContainer` 后、挂载应用前，用夹具已有的 `ioZone` 读取一次真实 `historyProvider`。这让串行录入队列在真实 I/O 时钟初始化，仍使用完整的真实数据库和生产 provider；其他等待、控件遍历、断言、超时和默认跳过策略保持原状。所有使用同一个 `mountRoot` 的测试是本次改动的影响范围。回滚只需删掉这次新增的一行。

在上述独立副本中，保留同一条 8 秒诊断与全部断言，场景完整遍历根页、设置和浮层，结果 `01:35 +1: All tests passed!`、退出码 0。诊断打印和 8 秒计时未写入正式测试。正式全量必须用 `-j 1 --reporter expanded` 不筛选执行；最终通过数、默认跳过数、文件覆盖范围和退出码以该次独立回执为准，定向通过不能代替最终结果。

聊天交付目录 `outputs/IK-Music-播放回归修复-20261126` 保留未完成轮次、隔离首红与同门修后日志、离线依赖身份以及正式全量回执。此票据和正式一行测试修复是保留的验收交付物。

## 连续两次启动根页面

在智能均衡预览的冻结前回归中，单例曾通过，但连续运行「迟启于搜索导航／有歌」「迟启于无悬停／有歌」时，第二例进入最近播放后，真实 `recordListen` 八秒仍不返回。独立的 `ProviderContainer` 不足以隔离这两个场景：测试整文件共享的 `AppDatabase` 还持有同一个 `HistoryDao`，其中的写队列能沿用已结束用例的时钟。

仅在此测试文件的数据库子类上，每例开始时用同一 SQLite 连接建立新的真实 `HistoryDao`；清空真实表、生产 provider、全部滚动和悬停、数据库与界面断言都保留。给该次等待设置明确的八秒上限，卡住会报告失败。相同的两个场景连续复验，125 秒，2 过、0 败；完整文件和无筛选套件另记结果。回滚只需还原测试文件中的数据库子类、每例初始化和该处等待上限，不影响已安装产品。

同一文件继续运行时，「播放准备与时长到达 → 搜索分类和歌词恢复」还暴露另一条故障：前例已经返回，下一例清表事务五秒未能进入回调。新增空事务等待不能消除问题。仅在此夹具用 Drift 的 `QueryInterceptor`，将真实连接的打开、开始事务、提交和回滚交由套件的 I/O 时钟调度；SQL 语句、事务回调、嵌套事务和异常传播均使用原实现。清表保留在每一例之前，八秒仍未完成即显示失败。移除该拦截器和清表等待上限即可回滚这一步。最终夹具无诊断打印，两组四例连续运行 143 秒，4 过、0 败。此前中止的全量运行不能作为冻结版的整仓结果。
